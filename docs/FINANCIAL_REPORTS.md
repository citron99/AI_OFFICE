# Финансовые отчёты синтетического пилота

В UI: «Бухгалтерия» → «Финансовый отчёт». API:
`POST /api/v1/accounting/financial-report` — read-only расчёт, разрешён viewer.

```json
{
  "start": "2026-07-01",
  "end": "2026-07-31",
  "planned_cash_in": "150000.01",
  "planned_cash_out": "290000.02"
}
```

Оба плана необязательны, но передаются вместе. План не сохраняется и не меняет
учётные данные. Максимум 366 дней; обратные даты, отрицательные суммы и доли
меньше цента отклоняются. Суммы сериализуются строками Decimal; float для расчётов
не используется. Даты включены, валюта только RUB, валютной конверсии нет.

## Методы и проверяемость

- Cash Flow: сумма income минус сумма expense из transactions в выбранном периоде.
- Сравнение: непосредственно предшествующий интервал той же длины. Для июля из 31 дня
  это 31 мая — 30 июня, а не календарный июнь. Изменение = текущий поток − предыдущий.
- План-факт: факт − введённый план отдельно для поступлений, выплат и чистого потока.
  Положительное отклонение выплат — превышение плана, а не улучшение результата.
- Задолженность: счета, выпущенные не позднее конца периода, минус все оплаты до этой
  даты включительно. Начало отчётного периода не отсекает старые долги и оплаты.
- Остаток по счёту = max(0, gross − paid); переплата = max(0, paid − gross).
  Переплата одному поставщику не уменьшает долг другому.
- Aging: срок не наступил (включая сам день оплаты), 1–30, 31–60, 61–90 и более 90 дней.
  Сумма корзин равна сумме остатков. Исходные invoice/payment/transaction IDs доступны
  в ответе и расшифровке интерфейса.
- Дебиторская задолженность: отдельные требования к покупателям, выпущенные до конца
  периода, минус уже полученные суммы. Для неё рассчитываются собственная расшифровка,
  общий остаток и те же проверяемые aging-корзины.
- Остатки денежных средств: последний доступный снимок каждого банковского счёта на дату,
  не позднее конца периода. Если снимка ещё нет, API возвращает `null`, а не фиктивный ноль.

Контроль июля 2026: поступления 151500.00, выплаты 300000.00, поток −148500.00 RUB.
Для приведённого плана отклонения: +1499.99, +9999.98 и −8499.99 RUB соответственно.

## Ограничения

P&L рассчитывается по отдельному синтетическому регистру начислений (ниже).
Денежный поток не является прибылью. Снимки банковских остатков не являются начальными
остатками для сверки cash flow. Cash transactions и invoice payments — разные синтетические
наборы без взаимной сверки. Специально заложенные аномалии не удаляются из отчёта:
для решения о черновике обязательны отдельные проверки AccountantAgent и policy gate.

Открытая часть FIN-001: полноценная бухгалтерская книга и сверка данных; ACC-004:
реальный импорт и обработка ошибок внешнего провайдера.
Журнал чтения mock-снимков реализован ниже, но не заменяет импорт реальной 1С.

## P&L по синтетическому регистру начислений

Провайдер предоставляет `AccrualJournal` с версией, периодом полного покрытия и
неизменяемыми записями `AccrualEntry`. Это учебный регистр, не бухгалтерская книга
двойной записи. Существующие cash/invoice fixtures не изменены и не стали источником
начислений автоматически. Отдельная версия: synthetic-accrual-rub-v2, покрытие 01.05–31.08.2026.

Дата recognised_on (в API `recognized_on`) определяет период независимо от оплаты.
Суммы в RUB без НДС, неотрицательные; reversal уменьшает соответствующую статью.
Дубликаты ID, записи вне покрытия и суммы с долями меньше цента запрещены.

- Выручка июля: 200000 − 10000 корректировки = 190000 RUB.
- Себестоимость 100000; валовая прибыль 90000 RUB.
- Операционные расходы 30000; амортизация 5000.
- Операционная прибыль 55000 RUB; в предыдущем равном периоде 40000; изменение +15000.

Финансовые расходы и налог на прибыль не представлены: чистая прибыль не заявляется.
Поэтому P&L и cash flow (−148500 RUB в июле) не должны совпадать. Их разница здесь
не является сверкой: это независимые тестовые наборы.

Период вне полного покрытия возвращает null, даже если в его части есть записи.
Пустой период внутри покрытия возвращает нули. Если провайдер не предоставляет
регистр, весь profit_and_loss равен null. В интерфейсе показаны оба периода,
версия, границы покрытия и записи с синтетическими основаниями.

## Журнал чтения синтетического снимка

POST `/api/v1/accounting/sync` с `{ "request_key": "unique-request-key" }` читает
Mock1C и сохраняет receipt: версию, SHA-256, количества и UTC-время. Повтор ключа
у того же владельца возвращает исходную запись; новый ключ фиксирует новое чтение.
GET `/api/v1/accounting/sync-runs` показывает до 100 последних записей владельца.
Viewer может читать историю, но не создавать записи. В интерфейсе доступны кнопки
«Проверить синтетический снимок» и «Журнал чтения».

Хеш покрывает версию, все семь коллекций и регистр начислений, а не только количества.
Исходные записи не копируются в БД: локальный Mock1C остаётся источником данных.
Это журнал успешных чтений неизменяемого mock-снимка, не полноценный ETL/import.
Ошибки внешнего источника и failed-sync не моделируются, реальная 1С не подключена.
