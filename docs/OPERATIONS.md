## Запуск и проверка

```powershell
docker compose -p ai-office-demo up -d --build
docker compose -p ai-office-demo ps
docker compose -p ai-office-demo logs --tail 100 api worker
uv sync --locked --dev
uv run python scripts/smoke_office.py --url http://127.0.0.1:8080
```

Скрипт создаёт явно синтетический источник, задачи и один mock-черновик.
UI доступен на 127.0.0.1:8080, API на 127.0.0.1:8000.
`/health` проверяет процесс; `/ready` проверяет БД, провайдер и Redis в queue-режиме.
Готовность Redis не означает наличие работающего worker: это проверяет сквозной smoke.
Остановка без удаления данных: `docker compose -p ai-office-demo stop`.
Не используйте `down -v`: это удалит сохранённые документы, задачи и БД.

## Пользовательский сценарий

1. В «Бухгалтерии» выберите inv_100 — чистый неоплаченный синтетический счёт.
2. На рабочем столе задайте вопрос о договоре и счёте, страну LV и дату 2026-08-27.
3. Для проверки policy gate выберите подготовку черновика. Дождитесь трёх проверок.
4. В «Согласованиях» отдельно одобрите действие. Повтор одного решения не создаёт дубль.
5. Для отрицательного сценария используйте inv_004: изменённые реквизиты блокируют действие.

Если юридических источников нет, результат прямо сообщает об этом. Даже разрешённый
mock-черновик имеет `legal_clearance=false`, `real_payment_allowed=false`. Юридического
разрешения и платежа нет. inv_001–006 содержат специально внесённые нарушения.

## Очередь, сбои и повтор

В Redis передаётся только ID, запрос хранится в PostgreSQL. PostgreSQL advisory lock
защищает от одновременного исполнения одного ID несколькими worker. После гибели worker
повторная доставка помечает незавершённую задачу failed, не выполняя её скрыто повторно.
В UI доступно «Повторить новой задачей», API: POST /api/v1/tasks/{id}/retry.
Это новая задача и новое согласование; исходная история сохраняется. Для сетевых повторов
передавайте `Idempotency-Key`: одинаковый ключ для одного исходного task ID возвращает ту же
новую задачу, не публикует её повторно и не дублирует событие аудита. Без ключа каждый retry
намеренно создаёт новую задачу.
Текущий exactly-once инвариант относится к одному approval, не ко всем задачам одного счёта.

Отмена кооперативная: уже отправленный вызов LLM может закончиться, но результат не должен
перезаписать отмену. Новая отмена задачи атомарно закрывает её pending approval как cancelled,
снимает requires_approval и пишет события task_cancelled/approval_cancelled. Повторная
отмена возвращает тот же результат без повторного аудита. В гонке с одобрением выигрывает
первая операция под блокировкой задачи; уже одобренный черновик отменой задачи не отзывается.
Старые записи, отменённые до этого исправления, автоматически не переписываются.
TTL согласования — 15 минут, проверяется при решении; просроченное
согласование не создаёт черновик. Dispatcher также завершает просроченные ожидания:
до 100 за цикл с паузой 10 секунд между циклами. Статус approval становится expired,
задача completed с результатом approval_expired, requires_approval=false; создаётся
одно событие аудита. Записи не удаляются. Отмена и уже принятое решение не перезаписываются.
Проверки истечения и восстановления очереди выполняются отдельно: отказ одной не
отключает другую. На PostgreSQL используется тот же порядок блокировок task → approval,
что и при решении владельца; занятые задачи пропускаются до следующего цикла.
Таблица задач служит durable outbox: отдельный dispatcher каждые 10 секунд повторно
отправляет до 100 queued задач старше 30 секунд. Это закрывает потерю сообщения между
commit и публикацией. Доставка at-least-once, повтор одного ID защищён worker-lock.
При явно обнаруженной ошибке отправки API возвращает failed с возможностью ручного retry.

## Доступ и секреты

По умолчанию demo owner без пароля. API_KEY режим настраивается одинаково для API и worker:
AUTH_MODE=api_key; AUTH_TOKEN_HASHES — JSON вида
`{"<SHA256 токена>":{"user_id":"owner-a","role":"owner"}}`.
Параметры .env автоматически не передаются контейнерам: добавьте их в общий environment
Compose или приватный override. Не коммитьте plaintext токены.
Роли: owner/admin разрешают согласование только своих ресурсов; service не согласует;
viewer имеет только чтение своего owner scope. Это не корпоративный SSO и не lifecycle IAM.
Токен в UI хранится в памяти до перезагрузки; смена токена очищает предыдущие данные.

Входной текст и журналы редактируются по шаблонам секретов; вложения и owner-visible
доказательства хранятся локально. Regex-DLP не гарантирует обнаружение всех секретов.
Аудит append-only на уровне приложения, но администратор БД способен его изменить.
LLM по умолчанию mock, юридическая генерация выключена. Никакие внешние платные вызовы
для приёмки этой версии не требуются. При включении внешнего LLM нужно отдельное согласование
политики обработки данных, ключи и проверка стоимости. Неизвестная стоимость в telemetry — null.

## Оставшиеся критерии полного продукта

- Независимая юридическая оценка и расширенный routing/RAG benchmark. Текущий semantic gate
  по отрицательным запросам не пройден; маленький синтетический набор не доказывает качество.
- Полные финансовые модели и отчёты по ТЗ, журнал синхронизации и дальнейшая сверка backlog.
- Нагрузочные и расширенные аварийные испытания, резервирование и проверка restore.
- SSO/жизненный цикл токенов, независимый security review, защита/retention файлов и аудита.
- Браузерная приёмка интерфейса, accessibility и пользовательские сценарии со специалистами.

Реальные 1С, банковские платежи и реальные данные не входят в текущий синтетический MVP.
