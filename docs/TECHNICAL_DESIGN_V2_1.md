# Technical Design V2.1 — AI-офис собственника

Этот документ заменяет раннее ТЗ V1.0 как описание фактической архитектуры
пилота. V1.0 полезно как перечень общих инвариантов (параллельность,
логирование, контроль стоимости и запрет внешних действий без человека), но
не определяет текущую топологию агентов.

## Назначение и границы

Пилот обрабатывает внутренние задачи владельца в трёх контурах:
Бухгалтер, Юрист и Безопасник. Он готовит проверяемый результат и, максимум,
черновик действия. Он не производит реальных платежей, не подписывает
договоры, не отправляет отчётность и не передаёт документы внешнему LLM до
security preflight.

Стек остаётся прежним: FastAPI, Pydantic v2, SQLAlchemy/Alembic,
PostgreSQL, Redis/Celery и React. `AccountingProvider` — строго read-only
контракт; mock-данные номинированы в рублях. Новой агентной платформы не
добавляется.

## Исполнение процесса

Сервер хранит `ProcessDefinitionV2` с версией, узлами, зависимостями, типами
выходов и `RunBudget`. При создании задачи снимок сохраняется вместе с ней.
`GraphExecutor` исполняет DAG слоями, атомарно claim-ит готовые шаги и запускает
независимые узлы параллельно. Каждый шаг имеет durable `node_id`, зависимости,
попытку, timestamp и отредактированный output.

Стандартный процесс `office_review`:

1. `accounting_snapshot` и `security_preflight` — параллельные корни.
2. `legal_review` — только после preflight.
3. `security_postflight` — только после всех выбранных проверок.
4. Детерминированный Policy Engine выдаёт `allow`, `deny` или
   `require_approval`; только последний открывает mock draft после отдельного
   approval.

Повторяемый `daily_cash_and_receivable_risk` строит бухгалтерский снимок,
после чего параллельно считает cash control и риск дебиторской задолженности.
Этот процесс запускается вручную API сейчас; ежедневное календарное
планирование будет включено только после согласования рабочего часового пояса
и графика владельца.

## Acceptance и доработка

Техническое выполнение и принятие результата — отдельные состояния.
Завершённая задача становится доступной для одного неизменяемого
`ResultReview`. Решение `rework_required` требует конкретных ID узлов.
Создаётся новый дочерний run с `rework_parent_task_id`, выбранными узлами и
счётчиком цикла; исходная задача остаётся историческим доказательством.

## Budget, безопасность и наблюдаемость

Для одного run лимитируются шаги, LLM-вызовы, rework, время, токены и рубли.
Оценка стоимости резервируется до узла, telemetry записывается после него.
Достигнутый лимит переводит run в `waiting_human`, а не в `failed`.

Audit хранит события и хэши, но не секреты и не chain-of-thought. Postflight
видит только структурированные контрольные поля. Все существенные действия
остаются за человеком. API `/processes/controls`, task trace и process graph
дают владельцу read-only наблюдаемость по рискам, policy и покрытию postflight.

## Условия production

Локальный пилот не является production-платформой. Перед подключением 1С,
настоящих моделей или нескольких компаний необходимы: корпоративная identity
и workspace/RBAC, секрет-хранилище, проверенные провайдеры/резервный маршрут,
лимиты уровня организации, PostgreSQL-конкурентные тесты и эксплуатационный
runbook. Эти условия намеренно не обходятся настройкой UI или prompt-ом.
